# BUG-003 : Un e-mail dont le domaine n'a pas de point est accepté (`a@g`)

| Champ | Valeur |
|---|---|
| **Famille** | Validation |
| **Sévérité** | Moyenne (S3) |
| **Priorité** | Moyenne (P3) |
| **Exigence violée** | AC-01.2, règle « domaine avec au moins un point entouré de caractères » |
| **Environnement** | minishop-app, `BUGS=BUG-003` ou `BUGS=on`, Node.js 22, Chromium (Playwright) |
| **Statut** | Ouvert (défaut volontaire, voir `minishop-app`) |

## Étapes de reproduction

1. Ouvrir « Inscription ».
2. Saisir l'e-mail `a@g` et un mot de passe valide (`Motdepasse-123`).
3. Valider.
4. Variantes : `a@g.` et `a@.com`.

## Résultat attendu

Message « Adresse e-mail invalide. », aucun compte créé (et `400 EMAIL_INVALID` côté API).

## Résultat obtenu

Le compte est créé : « Compte créé. Vous pouvez maintenant vous connecter. ». Le défaut est présent côté client **et** côté serveur, donc l'appel direct à l'API est lui aussi accepté.

## Impact

Comptes avec des adresses non délivrables : base polluée, e-mails de réinitialisation inutilisables, contournement de l'unicité par des adresses fantaisistes.

- `tests/e2e/register.spec.ts` : domaine sans point (`a@g`) et domaine terminé par un point (`a@g.`)
- `tests/api/register.api.spec.ts` : les trois variantes (`a@g`, `a@g.`, `a@.com`)

Ces tests utilisent `expectBug('BUG-003')` : en mode `BUGS=on` leur échec est attendu et rapporté comme réussi ; en mode `BUGS=off` ils doivent passer.
