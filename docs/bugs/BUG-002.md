# BUG-002 : Le serveur accepte un mot de passe trop court

| Champ | Valeur |
|---|---|
| **Famille** | Validation côté serveur |
| **Sévérité** | Moyenne (S3) |
| **Priorité** | Haute (P2) |
| **Exigence violée** | AC-01.3, AC-01.6, règle « 8 à 40 caractères, côté client et côté serveur » |
| **Environnement** | minishop-app, `BUGS=BUG-002` ou `BUGS=on`, Node.js 22, Chromium (Playwright) |
| **Statut** | Ouvert (défaut volontaire, voir `minishop-app`) |

## Étapes de reproduction

1. Envoyer directement à l'API, sans passer par l'interface :
   ```bash
   curl -i -X POST http://localhost:3000/api/register \
     -H 'Content-Type: application/json' \
     -d '{"email":"a@exemple.com","password":"abc"}'
   ```

## Résultat attendu

`400 {"code":"PASSWORD_LENGTH","message":"Le mot de passe doit contenir entre 8 et 40 caractères."}` et aucun compte créé.

## Résultat obtenu

`201 Created` : le compte est créé avec un mot de passe de 3 caractères. L'interface refuse bien la saisie : le contrôle n'existe que côté client.

## Impact

Contournement trivial de la politique de mot de passe par tout client qui parle directement à l'API. Comptes faciles à deviner par force brute.

[`evidence/BUG-002-mot-de-passe-3-caracteres-accepte.txt`](../evidence/BUG-002-mot-de-passe-3-caracteres-accepte.txt)

## Tests automatisés qui le détectent

- `tests/api/register.api.spec.ts` : mots de passe de 1 et 7 caractères refusés (valeurs limites)
- `tests/e2e/register.spec.ts` : les mêmes longueurs côté interface restent refusées (le défaut n'y est visible que par l'API)

Ces tests utilisent `expectBug('BUG-002')` : en mode `BUGS=on` leur échec est attendu et rapporté comme réussi ; en mode `BUGS=off` ils doivent passer.
